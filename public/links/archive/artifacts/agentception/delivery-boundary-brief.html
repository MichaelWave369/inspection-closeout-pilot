EXECUTION AUTHORITY · DELIVERY EVIDENCE · HUMAN ADMISSION

The ability to produce a change is not the authority to admit it.

Software execution crosses several distinct boundaries: dispatch, repository access, command execution, network use, secret access, file modification, check execution, pull-request creation, merge, deployment, and outcome verification. Each boundary needs its own declared authority.

Preflight must be explicit

Base state

Expected repository, base commit, clean-state requirement, branch policy, and concurrent-change assumptions.

File scope

Allowed and forbidden paths, generated files, binaries, migrations, lockfiles, and deletion authority.

Command scope

Allowed tools, shell posture, package managers, build commands, destructive commands, and time or resource limits.

External scope

Network access, package downloads, registries, APIs, credentials, secrets, webhooks, and third-party data.

Isolation is not a security certificate

A worktree, container, virtual environment, sandbox, or temporary branch can reduce interference while still being misconfigured, overprivileged, connected to sensitive credentials, vulnerable to dependency attacks, or able to affect external systems. The word isolated must never be used as proof of secure containment.

Checks are evidence, not proof

A passing test suite demonstrates only that the tests which actually ran produced passing results under that environment and input. Missing tests, incomplete assertions, flaky checks, stale fixtures, hidden dependencies, security defects, performance regressions, inaccessible systems, and misunderstood requirements may remain.

Generated ≠ correct · Tests passed ≠ safe · PR opened ≠ approved · Merged ≠ deployed · Deployed ≠ successful outcome

Pull-request boundary

A pull request candidate should preserve the base commit, changed files, diff summary, checks attempted, exact pass/fail results, unrun checks, warnings, issues, assumptions, scope changes, conflicts, and links to artifacts. It must not present omitted or skipped checks as passing.

Merge and deployment boundary

Only the repository’s authorized human and governance process may merge. Branch protections, required checks, protected dissent, code-owner review, security review, policy, licensing, and release rules remain binding. Deployment requires another explicit contract, and post-deployment observation must verify the intended operational outcome separately.

Secrets, supply chain, and data

The worker must not infer permission to read secrets, install dependencies, contact package registries, send telemetry, access private repositories, inspect user data, or call external services. Any required access must be declared, minimized, time-bounded, logged, and revocable. Dependency installation creates supply-chain risk even when the package name appears familiar.

Failure, cancellation, and cleanup

On failure or cancellation, the receipt should preserve commands attempted, partial modifications, processes started, artifacts produced, open handles, network activity, untracked files, and cleanup status. Cleanup must not delete the evidence needed to understand what happened. A later repair remains linked to the failed job.

Public workbench boundary

The Archive Delivery Workbench uses fixed synthetic records only. It does not accept repositories, files, patches, credentials, commands, packages, URLs, or code. It does not clone, branch, create worktrees, execute a shell, install dependencies, run tests, modify files, call models, access networks, open pull requests, merge, deploy, or persist visitor decisions.

Boundary: AgentCeption may prepare evidence-rich delivery candidates under a declared contract. It may not silently widen scope, invent authority, hide failed checks, treat isolation as security proof, treat tests as correctness proof, auto-merge, auto-deploy, or claim successful outcomes without separate verification.
